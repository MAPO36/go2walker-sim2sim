0.1 用到的框架和库
--------------------------------------------------------------------------------
  【仿真器】NVIDIA Isaac Gym Preview 4
      在 GPU 上并行跑物理仿真（PhysX 后端），4096 个环境同时训练。
      它不是一个“训练框架”，而是“物理世界 + 张量接口”。#tensor

  【训练环境框架】legged_gym
      来源：leggedrobotics/legged_gym（ETH Zurich Robotic Systems Lab），
            本仓库是 Unitree 维护的 fork（unitree_rl_gym）。
      作用：定义机器人环境的标准结构：
            观测怎么拼、动作怎么变成力矩、奖励怎么算、reset/终止怎么做、
            4096 个环境怎么管理、训练脚本和回放脚本怎么写。
      可以把它理解成“机器人强化学习的模板”。

  【强化学习算法库】rsl_rl
      来源：leggedrobotics/rsl_rl（同是 ETH RSL）。
      作用：实现 PPO、GAE、Actor-Critic 网络、rollout 存储、训练循环。
      legged_gym 只负责“环境和规则”，rsl_rl 只负责“怎么从经验里学”。

  【算法】PPO（Proximal Policy Optimization）
      一种 on-policy 的策略梯度算法。
      为什么选它：
        - 实现成熟、超参不敏感、训练稳定；
        - 天然支持大规模并行采样（4096 环境一次前向）；
        - rsl_rl 已经和 legged_gym 对接好，改环境不用改算法。
      为什么不用 DQN/SAC/TD3：
        - DQN 只能离散动作，机器人是连续 12 维；
        - SAC/TD3 是 off-policy，样本效率高但实现复杂，
          在大规模并行仿真里 PPO 的 wall-clock 效率反而更好；
        - 这个仓库的整套工具链就是围绕 PPO 写的。

  【深度学习框架】PyTorch 2.3.1
      网络定义、自动求导、GPU 训练、TorchScript 导出。

  【部署仿真】MuJoCo 3.2.3
      另一个物理引擎，用来做 sim2sim 验证。
      和 Isaac Gym 的 PhysX 不是同一个接触模型，所以能暴露“过拟合仿真器”的问题。

  【真机通信】unitree_sdk2py + DDS
      订阅 rt/lowstate（关节角、角速度、IMU），发布 rt/lowcmd（目标角 + Kp/Kd）。

  本机实际版本：
      Python 3.8（unitree-rl conda 环境）
      PyTorch 2.3.1
      MuJoCo 3.2.3
      NumPy 1.20.0
      Isaac Gym Preview 4（/home/ubuntu/IsaacGym_Preview_4_Package）

0.2 策略（policy）到底是什么
--------------------------------------------------------------------------------
  这里的“策略”不是一段 if-else 规则，而是一个神经网络：
      输入：47 维观测 s
      输出：12 维动作 a
      数学记法：π(a | s)

  具体结构（rsl_rl 的 ActorCritic）：
      Actor（策略网络）：
          47 -> 512 -> 256 -> 128 -> 12
          每层全连接，激活函数 ELU
          输出 12 个动作的均值 μ(s)
      Critic（价值网络）：
          50 -> 512 -> 256 -> 128 -> 1
          输出状态价值 V(s)（一个标量）
      动作分布：
          a ~ N(μ(s), σ²)，对角高斯
          σ 是 12 个可学习的参数（不是网络输出，和状态无关），初始 1.0
      训练时：
          从高斯分布采样动作 -> 有探索
      部署时：
          直接取均值 a = μ(s) -> 确定性
      参数量：
          Actor 约 19.0 万，Critic 约 19.0 万，合计约 38 万。

  为什么叫“非对称 Actor-Critic”：
      Actor 只看 47 维（真机能拿到的）；
      Critic 看 50 维（多 3 维机身线速度，只在训练时可用）。
      这样部署时 actor 不缺输入，训练时 critic 又能估得更准。

  策略和“控制”的分工：
      策略每 0.02 秒输出 12 个目标角偏移；
      PD 控制器每 0.005 秒（Isaac Gym）把目标角变成力矩；
      真正让关节动的是力矩，不是策略直接出力矩。

0.3 一张表看懂“谁负责什么”
--------------------------------------------------------------------------------
  层次            组件                     职责
  --------------------------------------------------------------------------
  算法层          rsl_rl / PPO             从经验里更新网络参数
  策略层          Actor MLP + Gaussian     观测 -> 动作
  价值层          Critic MLP               观测 -> 状态价值（只在训练时）
  控制层          PD 控制器                目标角 -> 力矩
  物理层          Isaac Gym / MuJoCo       力矩 -> 下一时刻状态
  环境层          legged_gym               观测拼装、奖励、reset、终止
  部署层          TorchScript + DDS        把 Actor 搬到 MuJoCo/真机
  --------------------------------------------------------------------------

1.1 一句话概括
--------------------------------------------------------------------------------
这个仓库做的事情是：

  在 NVIDIA Isaac Gym 里同时开 4096 只一模一样的 Go2 机器狗，让它们反复试错，
  用 PPO 算法训练一个神经网络。网络的输入是机器人“看到”的 47 个数（观测），
  输出是 12 个关节的目标角度偏移。训练好以后，把网络导出成一个 .pt 文件，
  再在 MuJoCo（另一个物理引擎）或真机上，用同样的观测和同样的 PD 控制去跑。

一句话：**用大规模并行仿真 + 强化学习，学一个“速度跟踪”的关节位置策略。**


1.2 四个阶段：Train → Play → Sim2Sim → Sim2Real
--------------------------------------------------------------------------------
这是 README_zh.md 里写的标准流程，也是理解整个仓库的骨架：

  Train     在 Isaac Gym 里训练。追求样本效率和稳定性，通常 --headless 不看画面。
  Play      在 Isaac Gym 里加载训练好的模型，用 1 个环境实时看效果，同时导出网络。
  Sim2Sim   把导出的网络放到 MuJoCo 里跑，检查策略是不是“只对 Isaac Gym 好使”。
  Sim2Real  把网络放到真机上跑，用 DDS 和电机通信。

为什么要 Sim2Sim？
  Isaac Gym 用的是 PhysX，MuJoCo 用的是它自己的接触模型，两者对摩擦、碰撞、
  关节阻尼的处理不一样。一个策略如果在 PhysX 里很好、到 MuJoCo 里就摔，
  说明它学到的可能是仿真器的“癖好”，不是真正的平衡能力。先过 MuJoCo 这一关，
  再去真机，风险小很多。

1.4 一次训练的完整数据流（最重要的一节）
--------------------------------------------------------------------------------
把 `python legged_gym/scripts/train.py --task=go2 --headless` 敲下去之后：

(1) 命令行解析
    helpers.get_args() 解析 --task、--headless、--num_envs、--max_iterations 等。

(2) 找任务
    train.py 里 `task_registry.make_env(name="go2")`。
    task_registry 是 legged_gym/envs/__init__.py 在 import 时填好的：
        task_registry.register("go2", GO2Robot, GO2RoughCfg(), GO2RoughCfgPPO())
    名字 "go2" 对应三个东西：环境类 GO2Robot、环境配置、训练配置。

(3) 建环境
    GO2Robot(cfg=..., sim_params=..., physics_engine=..., sim_device=..., headless=...)
    继承链：GO2Robot -> LeggedRobot -> BaseTask。
    - BaseTask.__init__：分配 obs/rew/reset 缓冲，创建 Isaac Gym 仿真和 4096 个环境。
    - LeggedRobot.__init__：解析配置、初始化状态缓冲、准备奖励函数。
    - GO2Robot：额外初始化足端状态、步态相位等。

(4) 建算法
    task_registry.make_alg_runner() 创建 OnPolicyRunner。
    它根据 env.num_obs=47、env.num_privileged_obs=50、env.num_actions=12
    构造 ActorCritic，再构造 PPO，再初始化 rollout storage。

(5) 训练循环（on_policy_runner.py 的 learn）
    每一轮迭代做两件事：
      A. 采样（rollout）：跑 num_steps_per_env = 24 个控制步。
         每一步：
           观测 obs (4096, 47)
             -> 策略网络输出动作均值
             -> 加高斯噪声采样动作 action (4096, 12)
             -> env.step(action)
                  -> PD 控制 -> 力矩 -> PhysX 仿真 4 个小步
                  -> 计算奖励、终止、新观测
             -> 存进 rollout storage
      B. 学习（PPO update）：
         用存储的 24×4096 = 98304 条经验，算 GAE、算 PPO 损失，
         分 4 个 mini-batch、跑 5 个 epoch，共 20 次梯度更新。

(6) 日志与保存
    每轮写 TensorBoard；每 50 轮存一次 model_<iter>.pt；1500 轮结束再存一次。

(7) Play
    play.py 只开 1 个环境，关掉噪声/摩擦随机化/推力，加载最后一个 run 的最后一个模型，
    用策略均值（不采样）跑 10 个 episode，并在开始时导出 Actor 为 TorchScript：
        logs/<experiment>/exported/policies/policy_1.pt

(8) Sim2Sim
    deploy_mujoco.py 读取同一个 .pt，按同样的观测布局和 PD 公式，
    在 MuJoCo 里每 0.02 秒算一次动作。

(9) Sim2Real
    deploy_real.py 读取 .pt，用 unitree_sdk2py 通过 DDS 收发 LowState/LowCmd，
    把关节目标角下发给电机驱动器。


1.5 配置系统：类的继承 + 字典化
--------------------------------------------------------------------------------
这个仓库的配置不是 YAML，而是 Python 类。好处是可以继承、可以写表达式，
坏处是新手容易看晕。

  BaseConfig                 空的基类（在 base_config.py）
    └─ LeggedRobotCfg        通用默认值：num_envs=4096、dt=0.005、奖励权重……
         └─ GO2RoughCfg      Go2 只覆盖“和通用不一样”的字段

例如 GO2RoughCfg 只改了：
  - init_state.pos = [0, 0, 0.42]
  - default_joint_angles（12 个关节）
  - env.num_observations = 47、num_privileged_obs = 50
  - control.stiffness/damping/action_scale/decimation
  - asset.file（go2.urdf）、foot_name、terminate_after_contacts_on
  - rewards.scales（16 项生效）
  - PPO 的 entropy_coef、experiment_name

没有覆盖的字段自动继承。比如 commands.ranges、terrain.mesh_type、
noise.add_noise、only_positive_rewards，Go2 都没有覆盖，所以用的是通用默认值。

class_to_dict() 会把嵌套类递归变成 dict，交给 rsl_rl 使用。
这也是为什么改配置时要注意：**你改的是类属性，不是字典**，
有些地方在 import 时就把配置实例化了，改的时候要确认改的是哪一份。

task_registry 里注册的是 `GO2RoughCfg()`（实例），不是类。
所以同一个进程里多次 get_cfgs 拿到的是同一个对象；play.py 会直接改它。
这在一个进程里只跑一个任务时没问题，但同时跑两个任务就要小心。


1.6 环境是怎么搭起来的
--------------------------------------------------------------------------------

1.6.1 4096 个并行环境
  env.num_envs = 4096。Isaac Gym 在 GPU 上同时模拟 4096 个机器人，
  每个环境有自己的根状态、关节状态、接触力。这是 PPO 能快速收敛的关键：
  一次前向就能收集 4096 条经验。

  环境间距 env_spacing = 3 米，机器人摆成一个网格，互不干扰。
  训练地形是平面（GO2RoughCfg 没有覆盖 terrain.mesh_type，默认 'plane'）。

1.6.2 从 URDF 到 Isaac Gym 资产
  asset.file = resources/robots/go2/urdf/go2.urdf
  Isaac Gym 加载后：
    - collapse_fixed_joints = True：把固定在机身上的零件合并，
      只留下 12 个可动关节（每腿 hip/thigh/calf）。
    - replace_cylinder_with_capsule = True：把碰撞圆柱换成胶囊，仿真更稳。
    - self_collisions = 1：关闭自碰撞（1 表示 disable，位掩码）。
  然后从 URDF 里读：
    - 12 个关节的名字、位置上下限、速度上限、力矩上限；
    - 4 个足端刚体的名字（foot_name = "foot"）；
    - base 这个刚体（用于终止判断）。

1.6.3 关节顺序（非常非常重要）
  URDF 里的可动关节顺序是：
      FL_hip, FL_thigh, FL_calf,
      FR_hip, FR_thigh, FR_calf,
      RL_hip, RL_thigh, RL_calf,
      RR_hip, RR_thigh, RR_calf
  即：左前 -> 右前 -> 左后 -> 右后，每条腿 髋/大腿/小腿。

  这个顺序同时决定了：
    - default_joint_angles 的书写顺序；
    - 策略输出的 12 个动作的顺序；
    - MuJoCo go2.xml 里 12 个电机的顺序；
    - 奖励里 hip_pos 用哪几个下标（Go2 是 [0, 3, 6, 9]）。

  如果从 g1 抄奖励，hip_pos 写的是 [1, 2, 7, 8]，那是 g1 的髋关节下标，
  抄到 Go2 就变成“惩罚大腿和小腿”，语义完全错。这是本项目实际踩过的坑。

1.6.4 PD 增益和默认角
  control.stiffness = {'joint': 20.}   # Kp = 20
  control.damping    = {'joint': 0.5}  # Kd = 0.5
  action_scale = 0.25
  decimation = 4
  默认角（弧度）：
      FL: 0.1, 0.8, -1.5
      FR: -0.1, 0.8, -1.5
      RL: 0.1, 1.0, -1.5
      RR: -0.1, 1.0, -1.5
  注意前后腿的大腿角不同（前 0.8、后 1.0），小腿都是 -1.5。
  这个不对称站姿是 Go2 的原厂站姿，训练和部署必须一致。
  初始高度 0.42 米，机器人会先掉几厘米落到地面，再开始控制。

1.6.5 摩擦随机化
  domain_rand.randomize_friction = True
  friction_range = [0.5, 1.25]
  每个环境从 64 个摩擦系数桶里随机抽一个，模拟不同地面。
  这是 sim2real 的关键：真机的地面摩擦不可能和仿真完全一样。

1.6.6 地形
  GO2RoughCfg 没有覆盖 terrain，所以是 'plane'（平面）。
  名字虽然叫 rough_go2，但这次训练用的是平地。
  如果以后要上台阶/斜坡，需要把 terrain.mesh_type 改成 heightfield/trimesh，
  并且注意观测里要不要加高度扫描（measure_heights）。


1.7 观测：策略的“眼睛”
--------------------------------------------------------------------------------

1.7.1 原始状态从哪来
  Isaac Gym 每个步长刷新这些张量：
    root_states   (num_envs, 13): [x, y, z, qx, qy, qz, qw, vx, vy, vz, wx, wy, wz]
    dof_state     (num_envs, 12, 2): [关节角, 关节角速度]
    contact_forces(num_envs, num_bodies, 3): 每个刚体的接触力
    rigid_body_states: 每个刚体的位姿和速度（Go2 用它取足端位置/速度）

1.7.2 两个坐标变换
  (a) 机身线速度/角速度
      root_states 里的速度是世界坐标系。策略需要的是“机身坐标系”下的速度，
      因为“往前跑”应该是 vx 为正，而不是随机器人朝向变化。
      做法是 quat_rotate_inverse(base_quat, world_vel)：
          v_body = R^T * v_world
      代码里用四元数实现，避免显式构造旋转矩阵。

  (b) 投影重力
      projected_gravity = R^T * [0, 0, -1]
      直觉：在机身坐标系里，“重力往哪个方向指”。
      - 站正时约 [0, 0, -1]；
      - 往前趴时会出现 +x 分量；
      - 往左倒时会出现 +y 分量。
      它比欧拉角更平滑、没有万向锁，是四足策略最常用的姿态观测量。

1.7.3 47 维逐位表（Go2 的接口契约）
  下标        内容                        缩放            噪声
  --------------------------------------------------------------------------
  0:3         机身角速度 [wx, wy, wz]      ×0.25           0.2 × 0.25
  3:6         投影重力 [gx, gy, gz]         ×1              0.05
  6:9         速度指令 [vx, vy, wz]         ×[2, 2, 0.25]   0
  9:21        关节角 - 默认角 (12)          ×1              0.01 × 1
  21:33       关节角速度 (12)               ×0.05           1.5 × 0.05
  33:45       上一步动作 (12)               ×1              0
  45:46       步态相位 sin(2πφ)             ×1              0
  46:47       步态相位 cos(2πφ)             ×1              0

  注意：
    - 机身线速度 base_lin_vel 不在 actor 的观测里（真机没有这个传感器）。
    - 上一步动作也放进观测，策略能看到自己上一拍输出了什么，有助于平滑。
    - 相位 sin/cos 是给策略的“节拍器”，让它知道现在该抬哪条腿。

1.7.4 缩放和噪声
  缩放是为了让不同量纲的数落在差不多的范围，网络更容易学。
  噪声只在训练时加，模拟真实传感器的抖动：
      obs += uniform(-1, 1) * noise_scale_vec
  noise_scale_vec 的下标必须和观测布局逐位对齐。
  Go2 的 _get_noise_scale_vec() 是按 47 维重写的；
  如果直接沿用基类的 48 维版本，噪声会整体错位（比如给指令加噪声变成给关节速度加噪声）。

1.7.5 critic 的 50 维
  actor 看 47 维；critic 看 50 维 = 47 + 机身线速度(3)。
  这叫“非对称 Actor-Critic”：
    - actor 只能看真机上能拿到的东西，部署时不会缺输入；
    - critic 只在训练时用，可以“开卷考试”，看到更多信息，估值更准，训练更稳。
  critic 的输出是一个标量 V(s)，用来算优势函数。

1.7.6 观测契约
  观测的维度、顺序、缩放、噪声位置，是训练端和部署端之间最重要的契约。
  任何一位对不上，程序不一定报错，但机器人会抽风、摔倒或者直接崩。
  本项目就踩过：训练端改成 47 维，MuJoCo 的 yaml 还写 48 维，
  报错是：
      RuntimeError: mat1 and mat2 shapes cannot be multiplied (1x48 and 47x512)
  记住这个教训：**改 compute_observations()，必须同步改部署端。**


1.8 动作：策略的“肌肉”
--------------------------------------------------------------------------------

1.8.1 12 维动作
  网络输出 12 个实数，对应 12 个关节。它们不是力矩，而是“关节目标角的偏移量”。

1.8.2 动作怎么变成目标角
      target_q = action * action_scale + default_angles
               = action * 0.25 + default_angles
  action 在 [-1, 1] 附近时，目标角在默认角附近 ±0.25 弧度（约 ±14°）内变化。
  这个缩放让策略的输出范围和控制精度匹配：太大容易抖，太小走不动。

1.8.3 PD 控制律
      tau = Kp * (target_q - q) - Kd * dq
  代码：pd_control(target_q, q, kp, 0, dq, kd)
  其中 Kp = 20，Kd = 0.5（每个关节相同）。
  物理直觉：
    - 位置误差越大，力矩越大，把关节拉向目标；
    - 速度越大，阻尼力矩越大，抑制抖动；
    - 没有积分项，避免积分饱和。
  力矩最后会被夹到 URDF 的 effort 上限：
    - hip/thigh：23.7 N·m
    - calf：35.55 N·m

1.8.4 decimation 和时间尺度
  sim.dt = 0.005 秒（物理步长）
  decimation = 4（每个控制步做 4 个物理步）
  所以控制周期 = 0.005 × 4 = 0.02 秒 = 50 Hz。
  策略每 0.02 秒输出一次动作；中间的 4 个物理步用同一个目标角。
  部署端（MuJoCo）用的是 dt = 0.002、decimation = 10，周期同样是 0.02 秒。
  这个 50 Hz 必须三端一致，否则手感和稳定性都会变。

1.8.5 为什么不用“直接出力矩”
  直接用 torque 作为动作，策略要自己学 PD 的稳定控制，样本效率低、容易抖。
  用“目标角 + PD”把低层控制封装起来，策略只需要学“往哪个方向抬腿”，
  这也是 legged_gym 系列的通用做法。
  代价是 PD 增益必须和训练一致；部署时改 Kp/Kd 等于换了控制器。

1.8.6 动作裁剪
  clip_actions = 100（配置默认），实际上等于不裁。
  真正限制动作范围的是 action_scale 和 PD/力矩限幅。


1.9 指令：策略的“目标”
--------------------------------------------------------------------------------

1.9.1 四个指令位
  self.commands 是 (num_envs, 4)：
      [0] vx      前后速度 [m/s]，+ 前进
      [1] vy      左右速度 [m/s]，+ 左移
      [2] wz      偏航角速度 [rad/s]，+ 左转
      [3] heading 目标航向 [rad]（只在 heading_command=True 时用）
  actor 只观测前三个。

1.9.2 每 10 秒重采样
  commands.resampling_time = 10 秒。
  _resample_commands() 对需要换指令的环境重新采样：
      vx ~ U(-1, 1)
      vy ~ U(-1, 1)
      如果 heading_command：heading ~ U(-3.14, 3.14)
      否则：wz ~ U(-1, 1)

1.9.3 小于 0.2 m/s 清零
      commands[:, :2] *= (norm(commands[:, :2]) > 0.2)
  这是训练时的一个约定：太小的线速度指令直接当成 0，
  避免策略去学“以 0.05 m/s 龟速挪动”这种没有意义的任务。
  副作用：策略几乎没见过 0.02~0.2 m/s 的慢速指令。
  键盘轻推如果只给 0.1 m/s，它会不知道怎么办；所以键盘按满用 0.8 m/s。

1.9.4 heading_command
  Go2 没有覆盖这个字段，所以继承默认值 True。
  这时 wz 不是每 10 秒随机一次，而是每一步由航向误差算出来：
      wz = clip(0.5 * wrap_to_pi(heading_target - current_heading), -1, 1)
  好处：策略学“朝目标方向转”，而不是“以某个角速度转”，转向更自然。
  注意：**训练时的 wz 指令大多数时候不是 0**，因为航向误差通常不为 0。
  这一点对第四部分的奖励门控很重要。

1.9.5 键盘模式（play.py / MuJoCo）
  Isaac Gym 的 play.py：
      commands.manual = True
      commands.heading_command = False
      commands.resampling_time = 1e9
      每个控制步把按键状态翻译成 commands[0, :3]。
  MuJoCo 的 deploy_mujoco.py：
      keyboard_control: true
      每 0.02 秒读一次 X11 键盘状态，翻译成 cmd。
  两条路径的共同点：没有按键时指令严格为 0。


1.10 奖励：策略的“分数”
--------------------------------------------------------------------------------

1.10.1 计算框架
  compute_reward() 做三件事：
    1. 对每个“权重非零”的奖励项，调用 _reward_<name>() 得到每只狗的原始分；
    2. 乘以权重，加到总奖励；
    3. 把总奖励加到 episode_sums，用于日志。
  在 _prepare_reward_function() 里，所有非零权重会先乘以 dt = 0.02。
  所以配置里写的权重是“每秒”的量纲，每一步实际乘 0.02。
  例如 tracking_lin_vel = 1.0，每步最多贡献 0.02，20 秒 episode 最多贡献 20，
  再除以 20 秒，TensorBoard 里就是 1.0。

  only_positive_rewards = True：
      每一步的总奖励如果小于 0，会被夹到 0。
      这意味着惩罚项不会让奖励变成负数，只是抵消正奖励。
      设计惩罚权重时不要指望“负分”能无限叠加。

1.10.2 16 项生效的奖励（Go2 配置）
  下面“权重”是配置里的数，“每秒最大贡献”是粗算，方便理解量级。

  (1) tracking_lin_vel  +1.0
      公式：exp(-||cmd_xy - v_xy||² / 0.25)
      含义：跟着线速度指令走。误差 0 得 1 分；误差 0.5 m/s 得 0.37；
            误差 1 m/s 得 0.018。主目标。
      收敛读数：0.8337（峰值 0.8504）。

  (2) tracking_ang_vel  +0.5
      公式：exp(-(cmd_wz - wz)² / 0.25)
      含义：跟着转向指令。主目标之二。
      收敛读数：0.4452（权重 0.5 时的满分是 0.5，归一化约 0.89）。

  (3) lin_vel_z  -2.0
      公式：vz²
      含义：别上下弹跳。

  (4) ang_vel_xy  -0.05
      公式：wx² + wy²
      含义：别左右摇、别前后翻。

  (5) orientation  -1.0
      公式：gx² + gy²（投影重力的水平分量）
      含义：机身别歪。改动前权重是 0，这是“走不出样子”的主因之一。

  (6) base_height  -10.0
      公式：(base_z - 0.25)²
      含义：机身高度保持在 0.25 米左右。改动前权重是 0，主因之二。

  (7) dof_acc  -2.5e-7
      公式：Σ((dq_prev - dq)/dt)²
      含义：关节别猛加速，动作平滑、省电机。

  (8) dof_vel  -1e-3
      公式：Σ dq²
      含义：关节别乱抖。

  (9) action_rate  -0.01
      公式：Σ(a_prev - a)²
      含义：相邻两步动作别突变。

  (10) dof_pos_limits  -5.0
      公式：超出软限位的量（软限位 = URDF 范围的 90%）
      含义：别把关节顶到限位。

  (11) alive  +0.15
      公式：1
      含义：活着就有分，鼓励别摔倒。每秒 0.15。

  (12) hip_pos  -1.0
      公式：Σ q_hip²，Go2 的下标是 [0, 3, 6, 9]
      含义：四条腿的髋关节别乱甩（别外八/内八太夸张）。

  (13) contact_no_vel  -0.2
      公式：Σ ||v_foot||² × contact
      含义：脚踩地时别还在地上蹭，减少滑步。

  (14) feet_swing_height  -20.0
      公式：Σ (z_foot - 0.08)² × (1 - contact)
      含义：抬起来的脚保持在 8 厘米高度附近，别抬太高也别拖着。

  (15) contact  +0.18
      公式：Σ_foot [ (contact 且处于支撑相) 或 (不 contact 且处于摆动相) ]
           其中支撑相 = leg_phase < 0.55
      含义：落脚时机要符合步态节拍。四只脚全对得 4 分，乘 0.18 得 0.72。

  (16) torques  -0.0002
      公式：Σ τ²
      含义：别用太大力气，省电、省电机。
      注意：这一项是从 Go2 原配置保留的（-0.0002），
            不是 g1 配方里的 -0.00001；保留是有意的。

  另外两个条目权重为 0，等于关闭：
      feet_air_time = 0.0
      collision     = 0.0
  termination 继承默认 -0.0，也是关闭。

1.10.3 步态相位和 contact 奖励
  period = 0.8 秒，offset = 0.5。
  phase = (episode_length_buf * dt) % 0.8 / 0.8
  leg_phase = [phase, phase+0.5, phase+0.5, phase]（对 1 取模）
  这个顺序对应 URDF 的 [FL, FR, RL, RR]：
      FL 和 RR 同相，FR 和 RL 同相 —— 对角小跑（trot）。
  contact 奖励检查每只脚“是否接触”和“当前是否应该支撑”是否一致。
  如果没有这个奖励，狗可能四条腿同时蹬地（跳着走）或者顺序混乱。

1.10.4 权重数量级
  正奖励：tracking 1.0 + 0.5，alive 0.15，contact 0.72，合计约 2.37/秒。
  负奖励：各项加起来在收敛时约 -0.57/秒（看 1.10.5 的读数）。
  净值约 1.8/秒，所以 only_positive_rewards 的裁剪通常不会触发。
  这也是为什么第四部分加一个 0.05~0.2/秒的惩罚是安全的：
  总奖励仍然为正，惩罚能起到“减少收益”的作用。

1.10.6 奖励设计的常见错误
  - 只加权重，不写对应的 _reward_ 函数 -> 启动时报 AttributeError。
  - 把权重写成“每步”的量级，忘了会乘 dt -> 奖励过大/过小。
  - 惩罚权重太大，总奖励被 only_positive_rewards 夹到 0 -> 梯度消失。
  - 惩罚了不该惩罚的东西：比如在转向时惩罚全部关节运动 -> 学不会转向。
  - 奖励里用了部署时拿不到的量（比如 base_lin_vel）-> 训练/部署不一致。
  - 奖励函数之间互相打架：比如同时要求“抬脚 8cm”和“关节别动”。
  - 改了奖励却沿用旧 checkpoint 声称“效果变好了” -> 不可比。


1.11 终止、重置、超时
--------------------------------------------------------------------------------
终止条件（check_termination）：
  1. 机身（base）接触力 > 1 N -> 摔倒/趴地；
  2. |roll| > 1.0 或 |pitch| > 0.8 -> 翻车；
  3. episode 长度超过 20 秒 -> 超时（不是摔倒）。
  超时和摔倒要区分：超时时 PPO 会用 V(s) 做 bootstrap（见 1.13.4），
  摔倒时不会，因为摔倒之后没有“未来”。

重置（reset_idx）：
  - 关节角 = 默认角 × U(0.5, 1.5)，关节速度 = 0；
  - 机身回到环境原点，高度 0.42；
  - 根速度随机 ±0.5（线速度和角速度都随机）；
  - 重新采样指令；
  - 清空动作、足端腾空时间、episode 计数。
  随机的初始关节角和初始速度是为了让策略见过各种起始状态，
  避免只会从“完美站姿”开始走。

episode 长度：
  episode_length_s = 20 秒，dt = 0.02 -> 1000 个控制步。
  训练日志里的 episode 长度达到 1002，说明最后策略几乎不摔。


1.12 域随机化
--------------------------------------------------------------------------------
  randomize_friction = True, range [0.5, 1.25]
  push_robots = True, 每 15 秒推一次，最大速度 1 m/s
  add_noise = True，观测噪声见 1.7.4
  这些都不是“为了让训练好看”，而是为了让策略在没见过的情况下也能活：
    - 摩擦变了也能走；
    - 被推一下能恢复；
    - 传感器有噪声也能用。
  这也是 sim2sim 有差距的原因之一：MuJoCo 里没有完全相同的随机化。


1.13 网络和 PPO
--------------------------------------------------------------------------------

1.13.1 Actor/Critic 结构（策略 = Actor）
  策略类型：对角高斯策略（diagonal Gaussian policy），属于
            “非对称 Actor-Critic + 可学习状态无关标准差”。
  Actor（就是“策略网络”π）:
      47 -> 512 -> 256 -> 128 -> 12，激活函数 ELU
      输出 12 维动作均值 μ(s)
  Critic（价值网络 V）:
      50 -> 512 -> 256 -> 128 -> 1，激活函数 ELU
      输出一个标量状态价值 V(s)
  参数量：Actor 约 19.0 万，Critic 约 19.0 万，合计约 38 万。
  噪声：另外有 12 个可学习的标准差参数（初始 1.0），
        与状态无关（不是 log-std 网络），只用于训练时采样。

1.13.2 高斯策略
  训练时：
      a ~ N(μ(s), σ²)
  部署时：
      a = μ(s)（取均值，不采样）
  采样带来探索；均值带来确定性。

1.13.3 PPO 的目标
  设 r_t(θ) = π_θ(a_t|s_t) / π_θold(a_t|s_t)，
      L_clip = E[ min( r_t A_t, clip(r_t, 1-ε, 1+ε) A_t ) ]
  ε = 0.2。
  直觉：新策略不能一步走太远；如果更新后概率比太大，梯度被截断。
  Critic 的损失是 (V(s) - return)²，也做了类似的裁剪。
  总损失 = PPO 损失 + 1.0 × 价值损失 - 0.01 × 熵。
  熵奖励鼓励探索，防止策略过早变得确定。

1.13.4 GAE（广义优势估计）
  δ_t = r_t + γ V(s_{t+1}) - V(s_t)
  A_t = δ_t + γλ A_{t+1}
  return_t = A_t + V(s_t)
  γ = 0.99，λ = 0.95。
  超时时：r_t += γ V(s_{t+1})，因为超时不是失败，未来还有价值。
  优势最后会做标准化：(A - mean) / std，让梯度尺度稳定。

1.13.5 自适应学习率
  每次更新算新旧策略的 KL 散度：
    - KL > 2 × desired_kl -> 学习率除以 1.5；
    - KL < 0.5 × desired_kl -> 学习率乘以 1.5；
    - 限制在 [1e-5, 1e-2]。
  desired_kl = 0.01。这样训练初期步子大，后期步子小。

1.13.6 超参数表
      gamma                 0.99
      lam                   0.95
      clip_param            0.2
      num_learning_epochs   5
      num_mini_batches      4
      learning_rate         1e-3（自适应）
      desired_kl            0.01
      entropy_coef          0.01
      value_loss_coef       1.0
      max_grad_norm         1.0

1.14 训练账本（数字要能对上）
--------------------------------------------------------------------------------
  并行环境数        4096
  每次迭代采样      24 步/环境 × 4096 = 98,304 条
  每次迭代仿真时间  24 × 0.02 秒 = 0.48 秒/环境
  1500 次迭代       98,304 × 1500 = 147,456,000 条经验
  折合机器人时间    147,456,000 × 0.02 秒 = 2,949,120 秒 ≈ 819 小时
  实际耗时          701.6 秒（约 11.7 分钟）
  吞吐              约 21 万条/秒

  这就是“大规模并行仿真”的威力：819 小时的机器人经验，11.7 分钟采完。
  PPO 每次迭代做 5 × 4 = 20 次梯度更新，每次 mini-batch 24,576 条。


1.15 play.py 与导出
--------------------------------------------------------------------------------
play.py 和 train.py 用的是同一套环境，但改了很多参数：
  num_envs = 1
  terrain 5×5（平地也无所谓）
  terrain.curriculum = False
  noise.add_noise = False
  randomize_friction = False
  push_robots = False
  env.test = True（让仿真按实时速度跑）
  commands.manual = True（默认，可用 RUN_MANUAL=0 关掉）
  commands.heading_command = False（否则 wz 会被航向控制器覆盖）
  commands.resampling_time = 1e9（禁止随机重采样）
  viewer.ref_env = 0

加载模型：
  get_load_path() 在 logs/<experiment>/ 下按名字排序，取最后一个 run，
  再在这个 run 里按名字排序，取最后一个 model_*.pt。
  注意：每次运行 train.py 都会新建一个按时间命名的目录。
  如果跑过 --max_iterations=2 的冒烟测试，那个目录会排在最后，
  play.py 会加载只训练了 2 轮的垃圾模型。跑完冒烟测试要把它删掉。

导出：
  EXPORT_POLICY = True
  调用 export_policy_as_jit()：如果是普通 MLP，导出 Actor（不是 Critic），
  保存为 logs/<experiment>/exported/policies/policy_1.pt。
  如果是 LSTM，导出 policy_lstm_1.pt（Go2 不是）。
  导出的只有网络权重和结构，**不包含奖励、配置、观测布局**。
  所以改了奖励/观测之后，旧 .pt 不能继续用，必须重新训练、重新导出。


1.16 MuJoCo sim2sim
--------------------------------------------------------------------------------
deploy_mujoco.py 做的事情：
  1. 读 yaml（策略路径、XML 路径、PD 增益、默认角、观测布局、num_obs、指令）；
  2. 加载 MuJoCo 模型和 go2.xml/scene.xml；
  3. 把机身放到 base_position，把 12 个关节设成 default_angles；
  4. 加载 TorchScript 策略；
  5. 循环：
       tau = Kp × (target_q - q) - Kd × dq
       写入 d.ctrl，mj_step 推进 0.002 秒；
       每 10 步（0.02 秒）：
         读 q、dq、四元数、角速度；
         用 build_observation() 重建 47 维观测；
         策略输出动作；
         target_q = action × 0.25 + default_angles。

  和训练端的对齐点：
    - 观测布局：47 维，humanoid（带 sin/cos 相位）；
    - 缩放：lin_vel 2.0、ang_vel 0.25、dof_pos 1.0、dof_vel 0.05；
    - 指令缩放：[2, 2, 0.25]；
    - PD：Kp=20, Kd=0.5；
    - action_scale=0.25；
    - 默认角；
    - 控制周期 0.02 秒；
    - 关节顺序。
  任何一项不对，表现都会变差。

  相位：
    deploy 用 sim_time % 0.8 / 0.8。
    训练用 episode_length_buf × 0.02 % 0.8 / 0.8。
    因为 20 秒 = 25 个 0.8 秒周期，训练时每次 reset 后相位从 0 开始，
    和部署从 t=0 开始是一致的。真机从任意时刻开始也没关系，
    相位只是一个周期节拍，差一个固定偏移不影响步态。

  键盘控制：
    见 go2.yaml 的 keyboard_control / keyboard_max_cmd / keyboard_commands。
    方向键上下左右 + K/L 转向。
    实现用 ctypes 调 X11 的 XQueryKeymap，每个控制周期读一次全部按键状态。
    不用 MuJoCo 的 key_callback，因为它在 3.2.3 里只在按下时触发一次，
    按住不重复、松开无事件，做不了“按住走、松开停”。


1.17 真机 sim2real（了解即可）
--------------------------------------------------------------------------------
deploy_real.py 用 unitree_sdk2py：
  - ChannelSubscriber 订阅 rt/lowstate，拿到关节角、关节速度、IMU；
  - ChannelPublisher 发布 rt/lowcmd，下发 12 个关节的目标角 + Kp/Kd；
  - RemoteController 解析遥控器的摇杆/按键，生成指令；
  - 状态机：先阻尼、再站起、再进策略。
Go2 用的是 "go" 消息类型（和 h1 一样），不是 g1/h1_2 的 "hg"。
仓库里 deploy_real/configs 目前只有 g1/h1/h1_2 的 yaml，没有 go2.yaml；
如果要做 Go2 真机部署，需要自己写一份，至少包含：
  control_dt、msg_type: "go"、imu_type、lowcmd/lowstate 话题、
  policy_path、leg_joint2motor_idx、kps、kds、default_angles、
  ang_vel_scale、dof_pos_scale、dof_vel_scale、action_scale、cmd_scale、
  num_actions、num_obs、max_cmd。
最重要的仍然是：观测、动作、PD、频率、关节顺序，和训练端逐位一致。

2.1 起点：Go2 当时是什么状态
--------------------------------------------------------------------------------
  - 在 legged_gym/envs/__init__.py 里，Go2 注册的是基类 LeggedRobot，
    没有自己的子类。g1/h1/h1_2 都有自己的子类。
  - go2_config.py 里观测还是 48 维（基类的布局：带 base_lin_vel、没有相位）。
  - 奖励权重表里只有 torques 和 dof_pos_limits 被手动调过，
    orientation 和 base_height 的权重是 0 —— 机身歪了不扣分、站太高太低不扣分。
  - 没有 Go2 自己的 MuJoCo yaml（上游仓库只有 g1/h1/h1_2）。
  - play.py 没有键盘控制。
  结论：能跑，但走不出样子；奖励几乎没在约束姿态。

2.2 七项改动
--------------------------------------------------------------------------------

【改动 1】新建 legged_gym/envs/go2/go2_env.py（GO2Robot 子类）
  为什么：基类没有 Go2 需要的一些量，直接改基类会影响 g1/h1/h1_2。
  做了什么：
    (a) 足端状态
        申请 rigid_body_state 张量，按 feet_indices 取出 4 只脚的
        位置 feet_pos 和速度 feet_vel。
        用途：feet_swing_height、contact_no_vel 两个奖励。
    (b) 步态相位
        period 0.8 秒，offset 0.5。
        legs 顺序 [FL, FR, RL, RR]，leg_phase = [φ, φ+0.5, φ+0.5, φ]
        （对角腿同相 = trot）。
        注意：g1/h1 只有两条腿，leg_phase 是两列；Go2 必须四列，
        否则 contact 奖励按脚遍历时会数组越界。
    (c) 47 维观测 compute_observations()
        去掉 base_lin_vel，末尾加 sin/cos。
    (d) 噪声尺度 _get_noise_scale_vec()
        按 47 维重新对齐每个下标。
    (e) 5 个奖励函数
        _reward_contact、_reward_feet_swing_height、_reward_alive、
        _reward_contact_no_vel、_reward_hip_pos。
        其余 11 项继承基类。

【改动 2】观测从 48 维改成 47 维
  为什么：
    - 真的 Go2 没有测机身线速度的传感器；仿真里能直接读，真机读不到。
      如果不删，将来 sim2real 必须重训。
    - 加 sin/cos 相位，让策略知道步态节拍。
  具体：
    旧 48：lin_vel(3) + ang_vel(3) + gravity(3) + cmd(3)
           + dof_pos(12) + dof_vel(12) + action(12)
    新 47：ang_vel(3) + gravity(3) + cmd(3)
           + dof_pos(12) + dof_vel(12) + action(12) + sin + cos
  同时：
    - go2_config.env.num_observations = 47
    - num_privileged_obs = 50（47 + 3 维 base_lin_vel，只给 critic）
    - 噪声向量按新布局重排
  必须同步的三个地方：compute_observations、num_observations、噪声下标。
  只改一个会报错或悄悄学歪。

【改动 3】把 g1 调好的奖励配方搬到 Go2
  为什么：原配置里 orientation=-0、base_height=-0，
          机器人歪着走、趴着走都不扣分，走不出样子。
  做了什么：在 go2_config.py 里配齐 18 个条目（16 项生效，2 项为 0）：
      tracking_lin_vel  +1.0
      tracking_ang_vel  +0.5
      lin_vel_z         -2.0
      ang_vel_xy        -0.05
      orientation       -1.0
      base_height       -10.0
      dof_acc           -2.5e-7
      dof_vel           -1e-3
      feet_air_time      0.0
      collision          0.0
      action_rate       -0.01
      dof_pos_limits    -5.0
      alive             +0.15
      hip_pos           -1.0
      contact_no_vel    -0.2
      feet_swing_height -20.0
      contact           +0.18
      torques           -0.0002
  细节：
    - hip_pos 的下标必须是 Go2 的 [0,3,6,9]，不是 g1 的 [1,2,7,8]。
    - torques 保留 Go2 原来的 -0.0002，没有照抄 g1 的 -0.00001。
    - 每一项都必须有对应的 _reward_ 函数，否则启动时 AttributeError。
  结果：orientation/base_height 开始生效，狗的姿态明显变好。

【改动 4】在 Isaac Gym 的 play.py 里接键盘
  为什么：训练完想看效果，但随机指令不好手动控制。
  数据流：
      按键事件 -> base_task.render() 写入 self.keys
      -> legged_robot._post_physics_step_callback() 读取
      -> 写 self.commands[0, :3]
      -> 观测 -> 策略 -> PD -> 狗动
  改了 4 个文件：
    - legged_robot_config.py：新增 commands.manual、manual_env_id、max_cmd，
      默认关闭，保证不影响训练。
    - base_task.py：无条件创建 self.keys（headless 也要有，
      否则 manual 分支一读就崩）；订阅 10 个按键；事件循环里记录按下/松开。
    - legged_robot.py：manual 模式下接管指令并 return，
      必须在航向控制之前 return，否则 wz 会被覆盖；
      _resample_commands() 在 manual 模式下直接返回。
    - play.py：num_envs=1、manual=True、heading_command=False、
      resampling_time=1e9。
  max_cmd = [0.8, 0.5, 1.0]，必须落在训练范围 ±1 内。

【改动 5】低速阈值的一个决定（没有改代码）
  训练时指令长度 < 0.2 m/s 会被清零。这意味着策略没见过 0.1 m/s 的慢指令。
  如果希望键盘轻推能慢走，需要把阈值改成 0.05 并重训。
  当时的选择：不改，键盘按满 0.8 m/s 使用。风险最低。

【改动 6】修 MuJoCo 的观测布局（deploy/deploy_mujoco/configs/go2.yaml）
  现象：
      python deploy/deploy_mujoco/deploy_mujoco.py go2.yaml
      RuntimeError: mat1 and mat2 shapes cannot be multiplied (1x48 and 47x512)
  原因：yaml 还是改动 2 之前的写法：
      observation_layout: quadruped
      num_obs: 48
  而新策略是 47 维 phase 布局。
  修改：
      observation_layout: quadruped -> humanoid
      num_obs: 48 -> 47
  （这里 "humanoid" 的意思是“带相位的那套布局”，不是“Go2 变人形了”。）
  实测：headless 跑 60 秒，前进 22.3 米，机身高度稳定在 0.28 米，没摔。
  注意：这条命令当时是允许改 deploy 配置的例外；代码没动。

【改动 7】MuJoCo 里改成“方向键走、松开就停”
  现象：
    - 一打开窗口狗就往前走；
    - WASD 和 MuJoCo 窗口快捷键冲突。
  原因（关键）：
    deploy_mujoco.py 里根本没有键盘代码。
    它每 0.02 秒把 yaml 里固定的 cmd_init 喂给策略。
    原来 cmd_init = [0.5, 0, 0]，所以一进去就永久 0.5 m/s 前进。
    这不是 bug，是它唯一收到的命令。
  修法：
    (1) cmd_init 改成 [0, 0, 0]；
    (2) 给 deploy_mujoco.py 加键盘控制。
  为什么不用 MuJoCo 自带的 key_callback：
    实测（真窗口 + XTest 真按键）：
        按下   -> 回调 1 次
        按住   -> 不再回调
        松开   -> 没有回调
    它无法表达“还按着”和“松开了”。
  改用 X11 的 XQueryKeymap：
    每 0.02 秒问 X 服务器“现在哪些键是按下的”，
    读的是全局物理状态，与窗口焦点无关。
    加了 3 个控制周期的松开防抖，避免 X11 auto-repeat 造成一顿一顿。
  键位（实测哪些键被窗口占用后选的）：
      方向键 上/下/左/右 -> 前进/后退/左平移/右平移
      K/L              -> 左转/右转
    Q/E 不能用，因为在这个 MuJoCo 版本里 Q/E 会切换显示选项。
  实测（真按键盘，跑真的 deploy 脚本）：
      空闲      命令 [0,0,0]      实测 [0.02,0.01]   原地
      按住 Up   命令 [0.8,0,0]    实测 [0.62,0.01]   2.5 秒前进 1.56 米
      松开      命令 [0,0,0]      实测 [0.04,0.01]   停住
      按住 Right命令 [0,-0.5,0]   实测 [0.03,-0.20]  右移 0.48 米
      按住 K    命令 [0,0,1]      ／                左转 89°
      按住 Down 命令 [-0.8,0,0]   实测 [-0.34,0.04]  后退 0.85 米
      按住 Left 命令 [0,0.5,0]    实测 [0.05,0.17]   左移 0.43 米
      按住 L    命令 [0,0,-1]     ／                右转 87°
      上+左     命令 [0.8,0.5,0]  实测 [0.61,0.26]   斜着走
  回归：g1.yaml 仍然从第 0 秒开始 0.5 m/s 前进，行为没变。
  因为键盘逻辑挂在 keyboard_control 开关后面，g1/h1/h1_2 的 yaml 没有这一项。

2.5 踩过的坑（按时间顺序）

  1. 观测维度三处不同步：compute_observations / num_observations / 噪声下标。
  2. yaml 没跟着 47 维改：1x48 vs 47x512 崩溃。
  3. 奖励函数没写：AttributeError。

  13. headless 下 self.keys 未创建：manual 分支崩溃。

3.1 三分钟讲清楚这个项目
--------------------------------------------------------------------------------
可以按这个顺序讲给朋友听：

  “我们养了 4096 只电子狗，在 GPU 上同时训练。每只狗有 47 个传感器读数
   （角速度、重力方向、速度指令、12 个关节角、12 个关节速度、上一步动作、
   两个步态相位），神经网络根据这些读数输出 12 个关节的目标角度。
   PD 控制器把目标角度变成力矩，物理引擎推进 0.02 秒，然后给狗打分：
   跟着指令走得分，摔了、歪了、抖了、费电了扣分。
   PPO 算法根据分数调整网络参数。训练 1500 轮，相当于 819 小时的狗生，
   实际只花了 12 分钟。最后把网络导出成一个文件，在 MuJoCo 和真机上
   用同样的观测和 PD 去跑。”

  如果对方问“为什么能这么快”：
     因为 4096 个环境是并行的，GPU 一次前向就采样 4096 条经验，
     而且模型很小（约 19 万参数）。

  如果对方问“为什么不用真机训练”：
     真机慢、贵、会摔坏；仿真里可以随便摔、随便随机化，
     学出一个鲁棒策略之后再迁移。

3.2 必答 15 问
--------------------------------------------------------------------------------
  Q1. 为什么观测是 47 维？每一维是什么？
  A1. 3 角速度 + 3 投影重力 + 3 指令 + 12 关节角 + 12 关节速度
      + 12 上一步动作 + 2 相位 = 47。机身线速度被去掉，因为真机测不到。

  Q2. 为什么 critic 看 50 维，actor 看 47 维？
  A2. 非对称 Actor-Critic。actor 只能用部署时拿得到的信号；
      critic 只在训练时用，可以多看 3 维机身线速度，估值更准。

  Q3. 动作是什么？为什么不是力矩？
  A3. 12 个关节目标角的偏移。目标角 = 动作×0.25 + 默认角。
      PD 控制器负责把目标角变成力矩。这样策略只学高层动作，
      低层稳定控制交给 PD，样本效率更高。

  Q4. PD 公式是什么？
  A4. tau = Kp(target_q - q) - Kd*dq，Kp=20，Kd=0.5。

  Q5. 控制频率是多少？
  A5. 50 Hz。Isaac Gym 物理步长 0.005 秒 × decimation 4 = 0.02 秒；
      MuJoCo 物理步长 0.002 秒 × decimation 10 = 0.02 秒。

  Q6. 奖励为什么乘 dt？
  A6. 配置里的权重是“每秒”的量纲。乘 0.02 变成每步的贡献，
      这样不同控制频率下的权重量级一致，日志里的 episode 值除以 20 秒也能对上。

  Q7. 为什么 only_positive_rewards 要把总奖励夹到 0？
  A7. 训练早期策略很差，负奖励会让价值函数很大、梯度不稳。
      夹到 0 相当于“最差也就是没分”，避免早期崩溃。代价是惩罚不能无限叠加。

  Q8. 指令为什么要清零小于 0.2 m/s 的？
  A8. 避免策略去学没有意义的龟速指令；0.2 以下直接当成站立。
      副作用是策略没见过慢速指令。

  Q9. heading_command 是什么？
  A9. 不直接给偏航角速度，而是给一个目标航向，每一步用航向误差算 wz。
      转向更自然，但训练时 wz 大多数时候不是 0。

  Q10. 为什么训练时加噪声，部署时去掉？
  A10. 训练加噪声模拟真实传感器抖动，让策略鲁棒；部署时真实传感器本身有噪声，
       不需要再人为加一遍。

  Q11. 为什么要有步态相位？
  A11. 给策略一个节拍器，告诉它现在该抬哪条腿。
      没有相位，四足容易学成跳着走或者顺序混乱。
      Go2 用对角小跑：FL/RR 同相，FR/RL 同相，周期 0.8 秒。

  Q12. PPO 的 clip 在干什么？
  A12. 限制新旧策略的概率比在 [0.8, 1.2] 内，防止一次更新把策略改得太远。
      这是 PPO 比普通策略梯度稳定的关键。

  Q13. GAE 在干什么？
  A13. 用多步回报估计优势，平衡偏差和方差。γ=0.99，λ=0.95。

  Q14. 为什么 sim2sim 会掉性能？
  A14. PhysX 和 MuJoCo 的接触模型、摩擦、阻尼不同；训练时的随机化也不能完全覆盖。
      78% 的跟踪率是正常范围，不代表配置错了。

  Q15. 为什么 0 指令还会慢慢往前蹭？
  A15. 策略本身有一个很小的残余偏置：tracking 奖励在速度接近 0 时是平的，
      梯度几乎为 0，所以它没有动力把最后 2.6 cm/s 压掉。
      这不是 MuJoCo 的锅（Isaac Gym 里也蹭，1.0 cm/s）。

3.3 反思：哪些做对了，哪些可以更好
--------------------------------------------------------------------------------
做对的：
  - 先读代码再改，确认了“Go2 用的是基类、没有子类”。
  - 从 g1 抄奖励时没有无脑复制，检查了 hip_pos 的下标和相位列数。
  - 先 smoke test（2 轮）再完整训练，节省时间。
  - 改完 MuJoCo 后用 headless 跑数字验证，而不是只看窗口。
  - 键盘功能做了真按键的端到端测试，不是只测代码路径。
  - 改了 deploy/ 共用脚本后，用 g1 做了回归。
  - 所有改动前都备份了原文件。
  - 把“需要人定夺”的问题单独列出来，没有擅自重训。

可以更好的：
  - 改观测维度时，应该同时检查部署端 yaml；这次是崩溃之后才补的。
  - 应该在文档里维护一张“观测契约表”，而不是靠记忆。
  - 0 指令漂移应该在训练结束时就测，而不是等到 MuJoCo 里才发现。
  - 奖励项的数量和语义应该写成表格，避免“17 项还是 16 项”这种模糊。
  - 冒烟测试目录应该在脚本里自动隔离，而不是靠人记得删。
  - 键盘控制的键位应该先做冲突探测，再写代码；这次是试出来的。
  - 训练日志只看了关键几项，应该把每一项的收敛曲线都过一遍。

4.5 细节与坑（务必逐条看）
--------------------------------------------------------------------------------
  1. 门控阈值必须和训练一致
     _resample_commands 用 0.2 清零；奖励门控也用 0.2。
     如果你以后改了清零阈值，两处要一起改。

  2. 不要惩罚“所有指令下的位置变化”
     那会把正常行走也惩罚掉。门控是关键。

  3. 不要惩罚 yaw 速度，除非真的 0 指令
     训练时 heading_command=True，wz 经常不为 0。
     如果你用 |wz| 门控，0 指令样本会非常少，学不到东西。
     方案 A 只用线速度门控，是安全的。

  4. 权重先小后大
     建议 -2.0 起步。一次加到 -20 可能让狗不敢动，
     甚至在非零指令时也畏手畏脚（因为梯度会泛化）。

  5. only_positive_rewards 的裁剪
     每步总奖励约 0.036（1.8/秒 × 0.02）。
     0.026 m/s 时，-2.0 的惩罚每步是 -0.052×0.02 = -0.00104，很小。
     不会触发裁剪。即使加到 -20，每步也只 -0.0104，
     仍小于正奖励，所以裁剪不是主要限制；主要限制是梯度会不会影响行走。

  6. 0 指令样本只有约 3.1%
     如果训练后发现 zero_cmd 项几乎没变化，可能是样本太少。
     方案 D（强制 10% 零指令）可以解决，但要重新训练并做 A/B。

  7. 推机器人会干扰测量
     训练时每 15 秒推一次；被推的瞬间速度大，惩罚会短暂变大。
     这是正常的。评测时（play/MuJoCo）没有推力，所以数字会更干净。

  8. 不要把奖励改动和观测改动混在一起
     这次只改奖励，观测保持 47 维。这样：
       - 不需要改 MuJoCo yaml；
       - 新旧策略可以直接对比（同一个观测接口）；
       - 出问题容易定位。
     如果同时改观测，两个变量混在一起，无法判断是谁的功劳。

  9. 旧 checkpoint 不能证明新奖励有效
     奖励不进 .pt，旧模型还是旧行为。
     必须重新训练、重新导出，才能声称“变好了”。

  10. 训练目录排序的坑
      play.py 取排序最后一个 run。冒烟测试会新建目录。
      每次冒烟测试后删掉那个目录，或者用 --run_name 区分。

  11. 导出的是 Actor，不是 Critic
      部署只需要 Actor。Critic 只在训练时用。
      所以改奖励不会影响导出文件的结构。

  12. 奖励函数里不要用 .item() 或 Python 循环
      所有计算都要是张量操作，否则会破坏 4096 个环境的并行。

  13. 如果加方案 C 的 action 惩罚
      self.actions 是经过 clip 后的动作，范围约 ±100；
      实际策略输出通常在 ±1 附近。sum(action²) 量级不大。
      权重 -0.02 起步，别用 -1。

  14. 训练时间
      1500 轮约 12 分钟。加一个奖励项不会明显变慢。
      如果变慢很多，检查是不是写了下标循环。

  15. 结果不可比的情况
      换了随机种子、换了 num_envs、换了观测、换了奖励，
      都不能直接和旧数字比。要做 A/B，只改一个变量。

4.6 验收标准（建议）
--------------------------------------------------------------------------------
  必达：
    - rew_tracking_lin_vel ≥ 0.7（原有验收线）；
    - Train/mean_episode_length 不明显低于 1002；
    - MuJoCo 方向键功能正常，前进/后退/平移/转向都对；
    - g1/h1/h1_2 不受影响。
  目标：
    - Isaac Gym 0 指令 20 秒漂移 < 0.05 米（优秀）/ < 0.10 米（可接受）；
    - MuJoCo 0 指令 20 秒漂移 < 0.10 米（优秀）/ < 0.20 米（可接受）；
    - 基线分别是 0.21 米和 0.52 米。
  不要追求的：
    - “绝对 0.000 米”。策略是随机的、仿真有数值噪声，
      而且 0 指令时还要保持平衡，理论上就会有微小的脚部调整。
      目标是把“肉眼可见的往前蹭”变成“肉眼看不出”。

4.7 排错表
--------------------------------------------------------------------------------
  症状：启动时报 AttributeError: 'GO2Robot' object has no attribute '_reward_zero_cmd_lin_vel'
  原因：配置里写了权重，但函数名拼错或没加。
  处理：函数名 = "_reward_" + 配置 key，逐字核对。

  症状：TensorBoard 里没有 Episode/rew_zero_cmd_lin_vel
  原因：权重为 0，或被 _prepare_reward_function 当成 0 丢弃。
  处理：确认配置里是非零值；确认改的是 GO2RoughCfg.rewards.scales。

  症状：zero_cmd 项一直是 0
  原因：门控从未触发（commands 里没有 0），或函数返回全 0。
  处理：打印 norm(commands[:, :2]) 的分布；确认训练时确实有 0 指令；
        确认 manual/heading 逻辑没有把 commands 覆盖掉。

  症状：狗不敢走，tracking 掉到 0.5
  原因：惩罚太大，梯度泛化到非零指令。
  处理：权重减半或减到 -1.0；检查门控是否写错（比如漏了 <0.2）。

  症状：狗站着时原地小碎步
  原因：线速度压住了，但关节还在动。
  处理：加方案 C 的 dof_vel 项，权重 -5e-3 起步。

  症状：狗被推一下就倒
  原因：站立时被惩罚得太死，不敢迈步恢复。
  处理：减小权重；保留 alive/orientation；考虑只在速度小于某阈值时惩罚
        （但会留下死区，不推荐一开始就用）。

  症状：MuJoCo 里漂移没变
  原因：play.py 加载了旧模型，或导出的路径不对。
  处理：确认 policy_1.pt 的时间戳；确认 play.py 加载的是正确的 run；
        重新导出。

  症状：MuJoCo 报 1x48 vs 47x512
  原因：又改回了 48 维布局，或 yaml 被改坏。
  处理：确认 observation_layout: humanoid、num_obs: 47。
