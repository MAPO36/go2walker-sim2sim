一、一句话总结
--------------------------------------------------------------------------------
以前：Go2 这个任务只是"把机型的配置文件填了一下"，机器人本身用的还是通用代码，
      眼睛（观测）里带着一个真机上根本测不到的信号，身上的奖励规则也几乎没调，
      所以走不出什么样子。
现在：给 Go2 单独写了一个"子类"，把这几个问题一次解决；重新训练了 1500 轮，
      速度跟随奖励从 0.19 涨到了 0.83（验收要求 0.7 以上），并且可以用键盘
      WASD / QE 直接开着机器人在仿真里走。


二、背景：这个项目是怎么组织的
--------------------------------------------------------------------------------
训练一个四足机器人走路，本质上是一个"试错"循环：

  1. 仿真里有 4096 只一模一样的机器狗，同时在地上乱动；
  2. 每只狗看一眼自己周围的状况（这个"看到的东西"叫 obs，观测）；
  3. 神经网络（策略）根据 obs 输出 12 个数字，代表 12 个关节想转到什么角度；
  4. 仿真推进一小步，根据"这一步做得好不好"给一个分数（reward，奖励）；
  5. 策略朝着"分数更高"的方向调整一点点。重复几百万次，它就学会走路了。

代码里三样东西各管一块：
  - legged_gym/envs/base/legged_robot.py      —— 通用逻辑（所有机器狗都一样的部分）
  - legged_gym/envs/go2/go2_config.py         —— Go2 的参数（关节角、PD 增益、奖励权重…）
  - legged_gym/envs/g1/g1_env.py 等           —— 某个机型有"特殊需求"时的子类

关键点：Go2 之前**没有**自己的子类，它在 legged_gym/envs/__init__.py 里是这么注册的：

    之前： task_registry.register("go2", LeggedRobot, ...)      <- 基类
    现在： task_registry.register("go2", GO2Robot,  ...)        <- Go2 自己的子类

g1 / h1 / h1_2 都有各自的子类，只有 Go2 是"裸奔"用基类的。这就是这次要补的第一课。

四、逐个说清楚每项改动
--------------------------------------------------------------------------------

【改动 1】新建 legged_gym/envs/go2/go2_env.py —— Go2 终于有自己的"出厂设置"
  这个文件里放了 5 件基类没有或不够用的事：

  (1) 足端状态 feet_pos / feet_vel
      基类只告诉你有多少接触力，但没有"脚现在悬在多高、以多快的速度移动"这种
      信息。而"抬脚高度""落地时脚别乱蹭"这类奖励必须用到它。
      做法是申请一张刚体状态表，从中挑出 4 只脚的 4 行。

  (2) 步态相位 phase
      想让狗"左右腿交替迈步"而不是"四脚乱蹬"，就要给它一个节拍器。
      phase 是一个在 0→1 之间循环的量，代表当前处于一个迈步周期的哪个位置。
      狗看一眼这个节拍，就知道"现在该抬哪条腿"。
      ⚠️ 这里 g1/h1 是两条腿（leg_phase 两列），Go2 是四条腿，所以这里改成了
         四列，顺序按 URDF 是 [左前, 右前, 左后, 右后]，
         对角腿同相（左前+右后一组，右前+左后一组），也就是"小跑步态 trot"。
         直接照抄 g1 的两列会让紧跟其后的 contact 奖励数组越界报错。

  (3) 47 维观测 compute_observations()
      见【改动 2】。

  (4) 噪声尺度 _get_noise_scale_vec()
      为了 sim2real（仿真里学会的拿到真机上也能用），训练时会被意往观测里加噪声，
      模拟真实传感器的抖动。加噪声的位置、幅度必须和新观测逐位对齐，否则
      比如"给指令加噪声"就变成了"给关节速度加噪声"，训练会莫名其妙地差。

  (5) 5 个新奖励函数
      见【改动 3】。

【改动 2】观测从 48 维改成 47 维 —— 这一步是为了将来少返工
  观测就是策略的"眼睛"。48 维里前 3 维是机身在 x/y/z 三个方向的线速度
  （base_lin_vel）。问题是：**真的 Go2 身上没有测量机身线速度的传感器**，
  仿真里能直接问你"现在跑多快"，真机上问不到。
  如果现在不删，将来做 sim2real（仿真→真机迁移）时必须重训一次。
  所以现在就把这 3 维删掉，换成 2 维的步态相位：

      旧（48 维）：机身线速度(3) + 角速度(3) + 重力方向(3) + 速度指令(3)
                  + 关节角(12) + 关节速度(12) + 上一步动作(12)
      新（47 维）：角速度(3) + 重力方向(3) + 速度指令(3)
                  + 关节角(12) + 关节速度(12) + 上一步动作(12) + 相位sin(1) + 相位cos(1)

  ⚠️ 有一处"必须同步改"的坑：观测维度写在 3 个地方，
     改了 compute_observations 就必须同时改 go2_config.py 里的
     num_observations，以及噪声尺度向量的下标。三个地方只要有一个没对上，
     训练会直接报错或者悄悄学歪。
  ⚠️ 机身线速度虽然从"眼睛"里删了，但并**没有消失**——它仍然留在 critic（评论家）
     网络的输入里（num_privileged_obs = 50 = 47 + 3）。这是 PPO 里的常见技巧：
     演员只能看真机上拿得到的东西，评论家只看分数、可以开卷考试，学得更稳。

【改动 3】把 g1 调好的奖励配方搬到 Go2
  奖励就是"给狗打分"。每一项是一个小函数，返回每只狗的得分，再乘以权重。
  改动前 Go2 的权重表里只有 torques 和 dof_pos_limits 两项被调过，其余
  全是模板默认值，其中最关键的两项正好是关闭的：
      orientation  = -0   （机身歪了不扣分 → 狗学会斜着身子走）
      base_height  = -0   （站太高太低不扣分 → 狗学会趴着走）
  这两项关着，就是"走不出样子"的主因。

  这次按 g1 的配方把 17 项配齐，并且**每一项都必须有对应的奖励函数**，
  否则训练时会报 AttributeError。这 17 项是：

      tracking_lin_vel   +1.0    跟着指令走，越快越准分越高
      tracking_ang_vel   +0.5    转向跟着指令
      lin_vel_z          -2.0    别上下弹跳
      ang_vel_xy         -0.05   别左右摇、别前后翻
      orientation        -1.0    别歪肩膀
      base_height       -10.0    身高保持在 25cm 左右
      dof_acc        -2.5e-07    关节别猛加速（省电机、动作平滑）
      dof_vel            -1e-3   关节别乱抖
      action_rate        -0.01   相邻两步动作别突变
      dof_pos_limits     -5.0    别把关节顶到限位
      alive              +0.15   活着就有分（鼓励别摔倒）
      hip_pos            -1.0    四条腿的髋关节别乱甩
      contact_no_vel     -0.2    脚踩地时别还在地上蹭
      feet_swing_height -20.0    抬起来的脚保持在 8cm 高度附近
      contact            +0.18   落脚时机要符合步态节拍
      torques        -0.0002     别用太大力气（省电、省电机）
      feet_air_time / collision  = 0，即关闭（权重为 0 的项会被自动忽略）

  ⚠️ 一个从别的机型抄奖励时必踩的坑：hip_pos 这一项，g1 写的是
     dof_pos[:, [1, 2, 7, 8]]，那是 g1 的髋关节位置。
     Go2 的关节顺序是 左前→右前→左后→右后，每条腿 髋/大腿/小腿，所以髋关节是
     [0, 3, 6, 9]。直接照抄会变成"惩罚大腿和小腿"，语义完全错。
     （这次是对着 resources/robots/go2/urdf/go2.urdf 重新数过的，已确认。）

【改动 4】接键盘：让 W/A/S/D 直接驱动机器人
  这是运行时功能，**不影响训练**，也不需要重训。
  按下 W 之后，数据是这样流动的：

      按 W
       → ① base_task.py 的窗口事件回调记录 self.keys['W'] = True
       → ② legged_robot.py 的 _post_physics_step_callback() 读到
       → ③ 算出 vx = 1.0 * 0.8，写进 self.commands[0, 0]
       → ④ compute_observations() 把 commands 放进观测
       → ⑤ 策略输出 12 个关节目标角 → PD 控制器 → 狗往前走

  具体动了 4 个文件：
    - legged_robot_config.py：新增 3 个开关 manual / manual_env_id / max_cmd，
      默认值保证"不打开就完全和以前一样"；
    - base_task.py：① self.keys = {} 必须**无条件**创建（放在 headless 判断外面），
      否则无窗口模式下手动分支一读就崩溃；② 订阅 10 个按键；③ 事件循环里加一个
      else 分支把按键状态存进 self.keys；
    - legged_robot.py：① _resample_commands() 开头提前 return，禁止随机改指令；
      ② _post_physics_step_callback() 开头接管指令，算完 **必须 return**，
      否则紧接着的航向控制逻辑会把我们的转向指令立刻覆盖掉；
    - play.py：num_envs 改成 1、打开 manual、关掉 heading_command 等。

  ⚠️ max_cmd（按键按满时的速度）必须落在训练时见过的指令范围内，否则
     "按下去狗不知道该怎么反应"。训练时线速度范围是 ±1.0，转向是 ±1.0，
     所以取 max_cmd = [0.8, 0.5, 1.0]。指令本身在这个范围内，键盘操作才安全。

【改动 5】关于"低速指令阈值"的一个决定（没有改代码）
  legged_robot.py 里有一行：指令长度小于 0.2 m/s 时会被清零（训练时用）。
  这意味着策略**几乎没见过 0.1 m/s 这种小指令**。
  如果希望键盘轻推能慢走，就需要把这行改成 0.05 并重训。
  这次的选择是：**不改**，键盘按满速用（0.8 m/s）。够用、风险最低。

【改动 6】修好 MuJoCo sim2sim 的观测布局
  （deploy/deploy_mujoco/configs/go2.yaml —— 这是跑下面这条命令报错之后补做的）

      python deploy/deploy_mujoco/deploy_mujoco.py go2.yaml

  报错长这样：

      RuntimeError: mat1 and mat2 shapes cannot be multiplied (1x48 and 47x512)

  大白话：策略的第一层是一张 47 列的表格，你却喂了 48 个数进去，乘法算不了。
  为什么配置会拼出 48 个数？因为这份 yaml 是【改动 2】之前写的。
  那时 Go2 用的还是基类那套老观测：

      线速度(3)+角速度(3)+重力(3)+指令(3)+关节角(12)+关节速度(12)+上一步动作(12) = 48

  而【改动 2】把"机身线速度"去掉（真机没有这个传感器），末尾加了 sin/cos 相位，
  变成 47 维：

      角速度(3)+重力(3)+指令(3)+关节角(12)+关节速度(12)+上一步动作(12)+sin+cos = 47

  所以 yaml 里两行必须跟着改：

      observation_layout: quadruped   ->   humanoid
      num_obs: 48                     ->   47

  "humanoid"这个名字有点误导：它指的是"带相位的那套布局"，
  g1/h1/h1_2 用它，Go2 从【改动 2】之后也用它 —— 不是说 Go2 变成了人形。
  为什么不干脆新起一个叫 go2 的名字？因为 deploy_mujoco.py 是 g1/h1/h1_2
  共用的文件，遵守"本次不动 deploy/ 代码"的约定，只改配置就够了，代码一行没动。

  这是个非常典型的坑：**观测的维度和顺序就是策略的"接口"**，训练端和部署端
  必须一位一位对齐。多一位、少一位、或者只是换个顺序，程序都不会提前警告，
  只会让机器人抽风、摔倒或者直接崩。以后凡是改了 compute_observations()，
  部署端的 yaml 就要同步改。

  实测（--headless，按配置跑满 60 秒）：

      t= 1.00s  base=[ +0.278  +0.038  +0.276]  vx=+0.388 m/s
      ...
      t=60.00s  base=[+22.284  +1.225  +0.279]  vx=+0.443 m/s

  60 秒前进 22.3 米，机身高度全程稳在 0.28 米，没摔。
  指令是 0.5 m/s，实际跑出 0.35~0.44 m/s，约 76%。训练时（无噪声、理想条件）
  日志里的跟随分也只有 0.85 左右，而且 MuJoCo 的接触模型和 Isaac Gym 并不完全
  一样，这个差距是正常的，不是配置又错了。

【改动 7】MuJoCo 里改成"方向键走、松开就停"
  （deploy/deploy_mujoco/deploy_mujoco.py 和 configs/go2.yaml）

  用户看到的现象：一打开窗口，狗就自己往前走；而且想用 WASD 遥控时发现
  跟 MuJoCo 窗口自带的快捷键打架。

  先说"为什么会自己走"，这个和键盘一点关系都没有：

      cmd_init: [0.5, 0, 0]      # 配置文件里的一行

  MuJoCo 版的 deploy 脚本**根本没有读键盘的代码**。它每 0.02 秒把配置里这个
  固定不变的指令喂给策略，从第 0 秒到第 60 秒都是"向前 0.5 m/s"，
  所以狗一进去就在走——那不是 bug，是它唯一会做的事。

  修法分两步：

  (1) 把 cmd_init 改成 [0, 0, 0]：没按键时指令是 0，策略就在原地站着。
      为什么 0 指令它站得住？因为训练时"指令长度小于 0.2 m/s 会被清零"，
      所以"全零指令"是它训练时见过最多的情况之一，它学过该怎么站。

  (2) 给 deploy_mujoco.py 加键盘：按着键时就一直走，松开就停。

  ── 为什么不能用 MuJoCo 自带的键盘回调 ──
  MuJoCo 提供了 launch_passive(..., key_callback=...)，看起来正好能用。
  但实测（在真窗口上用 XTest 真的按键）发现它只给一种事件：

      按下 Up   -> 回调响 1 次
      按住不放  -> 不再响了
      松开      -> 完全没有事件

  也就是说，它只能告诉你"某个键被按下了"，永远不知道"这个键还按着"
  或者"这个键松开了"。而"松开就停"恰恰需要后面这两个信息。

  所以换了个办法：直接问 X 服务器"现在键盘上哪些键是按下的"。
  X11 有个函数叫 XQueryKeymap，一次返回全部按键的当前状态（物理状态，
  不是事件流）。部署脚本每个控制周期（50 Hz，也就是 0.02 秒一次）问一次，
  于是"按着不动就一直走、松手立刻归零"自然就成立了。
  顺带的好处：它读的是服务器的全局状态，和哪个窗口有焦点无关，
  鼠标悬在窗口上、甚至窗口没被点中也照样能按。

  另外加了一个小保险：一个键要连续 3 个周期都被读成"松开"才真的算松开。
  原因是 X11 的按住连发（auto-repeat）是"松开+按下"两个事件拼出来的，
  万一正好在那一瞬间采样，会读到 1 个周期的"松开"，狗就会一顿一顿的。
  3 个周期 = 0.06 秒，肉眼看不出延迟。

  ── 键位是怎么选的 ──
  同样是实测出来的：我写了个探针程序，把候选键一个个真按一遍，看 MuJoCo
  窗口自己的显示开关有没有被改掉。结果是这些键都被窗口占用了：

      A D Q E C V B M T Y U J O 以及数字键 1 0 2 和 , ; Tab ' \ `

  所以：

      方向键 上/下/左/右   -> 前进 / 后退 / 左平移 / 右平移
      K / L               -> 原地左转 / 原地右转

  K/L 而不是 Q/E，是因为 Q 和 E 在这个版本的 MuJoCo 里正好会切换窗口的
  显示选项（Q 切相机标记、E 切约束标记）。在 Isaac Gym 的 play.py 里 Q/E
  是转向键，但那边的窗口没有这些快捷键，所以两边键位不一样是有意的。
  方向键里只有"左/右"被窗口拿去当"暂停时单步前进/后退"，不停的时候没有影响。

  键位写在 go2.yaml 里，想换直接改配置就行：

      keyboard_control: true
      keyboard_max_cmd: [0.8, 0.5, 1.0]      # 按满时的 [前后, 左右, 转向]
      keyboard_commands:
        Up:    [1.0, 0.0, 0.0]               # 前进
        Down:  [-1.0, 0.0, 0.0]              # 后退
        Left:  [0.0, 1.0, 0.0]               # 左平移
        Right: [0.0, -1.0, 0.0]              # 右平移
        k:     [0.0, 0.0, 1.0]               # 左转
        l:     [0.0, 0.0, -1.0]              # 右转

  同时按两个键是**相加**的：按住"上+左"就是斜着走。相加后每个轴裁剪到 ±1，
  再乘以 keyboard_max_cmd。0.8/0.5/1.0 这三个数和 Isaac Gym 的 play.py 一致，
  也都在训练范围内（训练时三个轴都是 ±1），所以两个仿真器手感一样。

  ── 实测（真按键盘，跑的是真的 deploy 脚本，不是模拟） ──

      时间窗口          命令[vx vy wz]        实测机身[vx vy]      这 2.5 秒

      按住 Up           [+0.80 +0.00 +0.00]   [+0.62 +0.01]        前进 1.56 m
      松开后            [+0.00 +0.00 +0.00]   [+0.04 +0.01]        停住
      按住 Right        [+0.00 -0.50 +0.00]   [+0.03 -0.20]        右移 0.48 m
      松开后            [+0.00 +0.00 +0.00]   [+0.02 +0.01]        停住
      按住 k            [+0.00 +0.00 +1.00]   [+0.03 -0.03]        左转 89°
      松开后            [+0.00 +0.00 +0.00]   [+0.02 +0.01]        停住
      按住 Up+Left      [+0.80 +0.50 +0.00]   [+0.61 +0.26]        斜着走

  前进跟得最准（0.8 指令跑出 0.62，78%），转向其次（1.0 rad/s 跑出 0.62，
  62%），平移最弱（0.5 跑出 0.2，40%）——这些都和 Isaac Gym 里同一个策略的
  表现量级一致，MuJoCo 和 Isaac Gym 的接触模型不同，有差距是正常的。

  ── 一个还没完全解决的问题（可能需要人来定夺） ──
  指令为 0 时，狗是**站着的，但会慢慢往前蹭**：MuJoCo 里 20 秒挪 0.52 米
  （约 2.6 cm/s）。我特意回到 Isaac Gym 里用同一个策略、同样给 0 指令测了
  20 秒：也蹭，0.21 米（约 1.0 cm/s）。也就是说**这不是 MuJoCo 移植的问题，
  是策略本身的脾气**——它嘴里说"站着"，实际有个很小的匀速偏置。

  想让"0 指令 = 完全钉死"，只能改策略重训（比如在 0 指令时惩罚位移），
  而且不保证能彻底消除。按用户要求，涉及重训的事只报告、不擅自做。
  对"按键就走、松手就停"这个需求来说，现在这个程度够用：一秒钟挪 2.6 厘米，
  肉眼看着就是站着。

  回归验证：g1.yaml（自带预训练策略）跑起来仍然和以前一模一样，从第 0 秒
  就按 0.5 m/s 前进，说明共用脚本没被改坏；g1/h1/h1_2 的配置里没有
  keyboard_control 这一项，代码里默认就是关的，它们的行为一行没变。

六、怎么自己跑起来
--------------------------------------------------------------------------------
（假设已经在 conda 环境里；注意这个仓库必须用 unitree-rl 这个环境）

  训练：
      cd /home/ubuntu/B4_2025/unitree_rl_gym
      python legged_gym/scripts/train.py --task=go2 --headless

  导出策略：
      python legged_gym/scripts/play.py --task=go2

  用键盘开机器人（需要图形界面）：
      python legged_gym/scripts/play.py --task=go2
      然后按 W/S 前后、A/D 左右、Q/E 原地转向

  想看不接键盘时机器人自己走（验证策略本身）：
      RUN_MANUAL=0 python legged_gym/scripts/play.py --task=go2

  用 MuJoCo 跑（sim2sim，需要图形界面，见【改动 6】【改动 7】）：
      python deploy/deploy_mujoco/deploy_mujoco.py go2.yaml
      进去先站着不动，然后：
          方向键 上/下  前进 / 后退
          方向键 左/右  左平移 / 右平移
          K / L         原地左转 / 原地右转
          （同时按多个键 = 斜着走；松手就停）

  不看窗口、只跑一遍出数字（不需要显示器）：
      python deploy/deploy_mujoco/deploy_mujoco.py go2.yaml --headless
      这种模式下没有键盘（也读不到），机器人按 cmd_init 的指令行动，
      即 [0,0,0] —— 原地站着。


七、遗留问题（需要人来定夺的）
--------------------------------------------------------------------------------
1. deploy/deploy_mujoco/configs/go2.yaml —— 已经修好了（见【改动 6】）。
   原来它写的是"48 维观测 + quadruped 布局"，指的是新代码之前那套
   基类观测（多 3 维 base_lin_vel、没有相位）。这一条当初被记成
   "任务范围禁止改 deploy/，所以没动"，结果真的踩了：直接跑
   deploy_mujoco.py go2.yaml 会报

       RuntimeError: mat1 and mat2 shapes cannot be multiplied (1x48 and 47x512)

   意思是配置拼出 48 个数，而策略的第一层只收 47 个。
   现已把 observation_layout 改成 humanoid、num_obs 改成 47，
   实测能走（60 秒前进 22.3 米）。
   （【改动 7】之后 deploy_mujoco.py 被动过了——那是应要求加键盘控制，
   改动全部由 keyboard_control 开关控制，关掉时行为和原来完全一致。）

2. ⚠️ 0 指令时狗会以约 2.6 cm/s 慢慢往前蹭（MuJoCo 里 20 秒 0.52 米）。
   原因已查明：Isaac Gym 里同一个策略、同样 0 指令，20 秒也蹭 0.21 米
   （约 1.0 cm/s）。所以这是策略本身的残余偏置，不是 MuJoCo 移植的锅。
   要彻底钉死只能改策略重训，且不一定能消除——按约定没有擅自重训。
   详见【改动 7】最后一节。

3. torques 权重保留了 Go2 原有的 -0.0002（新的奖励清单里没有列出这一项，
   它继承的是模板默认 -0.00001）。保留原值是有意为之——这是 Go2 专门调过的
   数值，改小 20 倍会让电机更容易发热。如果希望严格照抄 g1 配方，把这一行
   删掉即可。

4. 低速指令阈值仍然是 0.2（见【改动 5】），键盘轻推不会有慢速效果。

5. Isaac Gym 那边（play.py）的键盘按键的"真实按键事件"（真的按下去）
   只能在有图形界面时人工验证。自动化脚本是直接写 env.keys 来跑的——
   这正是窗口回调做的事，所以逻辑链路已经验证过，但没有验证 Isaac Gym
   的窗口事件订阅本身。MuJoCo 这边（【改动 7】）是真按键盘验证过的。

6. 旧模型 logs/go2_1/exported/policies/policy_1.pt 是 48 维的，
   和新代码不兼容（观测维度变了）。旧 .pt 立即作废，这是正常现象，
   不是 bug——奖励和观测只在训练时起作用，不会被存进 .pt 文件里。

7. ⚠️ 有个容易踩的坑：每次运行 train.py 都会在 logs/rough_go2/ 下新建一个
   "日期_时间_" 目录，而 play.py 加载的是**按名字排序后最后一个**目录。
   如果你跑完冒烟测试（--max_iterations=2）紧接着跑 play.py，
   它会去加载那个只训练了 2 轮的垃圾模型，而不是你辛苦训练出来的模型
   （症状：机器人一动不动，或者乱抽搐）。
   解决办法：冒烟测试跑完后，把那个只含 model_0.pt / model_2.pt 的小目录删掉。
   本次已经清理过，现在 logs/rough_go2/ 下只剩真正训练的那一份。
